# Authentication

How callers authenticate to the Catalog Service, and why the scheme was chosen.

**Decision status**: Accepted · 2026-10-29 (see *Decision record*)

---

## How to authenticate

Every data endpoint requires an API key, sent in the `X-API-Key` request header over HTTPS.

```bash
curl -s -H "X-API-Key: $CATALOG_API_KEY" \
  "https://catalog.builtbykromha.com/products/search?occasion=housewarming&max_price=60"
```

| Route | Key required |
|---|---|
| `GET /categories`, `GET /categories/{category}/products`, `GET /products/search`, `GET /products/{product_id}` | Yes |
| `GET /health`, `GET /openapi.json`, `GET /docs`, `GET /redoc` | No. They contain no catalogue data; the OpenAPI document is published publicly on purpose |

There are no sessions, tokens to exchange or expiries: the key itself is sent on every request.

### Responses

A missing or invalid key:

```http
HTTP/1.1 401 Unauthorized

{"error": {"code": "unauthorized",
            "message": "Missing or invalid API key.",
            "hint": "Send a valid key in the X-API-Key header."}}
```

More than 120 requests in a minute on one key:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 20

{"error": {"code": "rate_limited",
            "message": "Too many requests for this API key.",
            "hint": "Retry after the number of seconds in Retry-After."}}
```

## Keys

- **One key per consumer and environment.** Each can be revoked without affecting the others.

  | Key | Holder |
  |---|---|
  | `platform-test` | indigo.ai workspace, Test environment |
  | `platform-prod` | indigo.ai workspace, Production environment |
  | `local-dev` | Developer machine |

- **Issuing.** Keys are generated by the service operator (`python3 -c "import secrets; print(secrets.token_urlsafe(32))"`) and handed over through a secret store, never by email or chat.
- **Service side.** The service reads every valid key from the `CATALOG_API_KEYS` environment variable (comma-separated). It compares in constant time against each, and **refuses to start if the list is empty**, so it can never run unprotected by accident.
- **Logging.** Requests are logged with the key's fingerprint (the first 6 hex characters of its SHA-256), never the key itself.

Storage rules for each secret: `docs/guides/secrets-management.md`.

## Connecting the indigo.ai agent

The platform does not read `securitySchemes` from the OpenAPI document. The header has to be configured on the tool collection.

1. **Workspace settings → Secrets**: create `CATALOG_API_KEY`, with the `platform-test` key as its **Test** value and the `platform-prod` key as its **Production** value.
2. In the Catalog tool collection's headers, add `X-API-Key` with the value `[[CATALOG_API_KEY]]`, inserted with **Add secret**. The reference must be the **entire** header value.
3. Save, check a tool call in the Test environment, then Publish the workspace.

The platform resolves the secret server-side; it never reaches the LLM, the conversation or the platform logs.

## Key rotation

Rotation needs no downtime, because the service accepts several keys at once:

1. Add the new key to `CATALOG_API_KEYS` next to the old one, and restart the service.
2. Update the consumer (for the platform, the secret's Test or Production value).
3. Confirm calls succeed and the logs show the new fingerprint.
4. Remove the old key and restart. Confirm the old key now gets `401`.

Full procedure: `docs/guides/secrets-management.md`. Rotate straight away if a key appears in a commit, log, transcript or screenshot.

## Implementation notes

- The OpenAPI document declares an `apiKey` security scheme on `X-API-Key`, for `/docs` and for human readers.
- `X-API-Key` is **not** declared as a header parameter on any operation. The platform would show a declared parameter to the LLM as a value to fill in.
- The rate limit is kept in memory per key fingerprint. That is enough for a single instance; it would need a shared store if the service ever scaled out.

## Decision record

**Status**: Accepted · 2026-10-29

### Context

- The only caller is the indigo.ai platform. Its tools authenticate **only through configured HTTP headers**. Values come from workspace secrets referenced as `[[NAME]]`, which must be the entire header value. `securitySchemes` in the OpenAPI document are ignored, and there is no native OAuth 2.0.
- Secrets have separate Test and Production values, are resolved server-side, and never reach the LLM, the logs or the user.
- The data is low-sensitivity: it is the shop's public catalogue, and raw stock counts are never exposed. The realistic threat is a leaked key being used to scrape or overload the service, not data theft.
- The brief requires the endpoints to be protected, and how a caller authenticates to be documented.

### Options considered

| Option | Verdict | Reason |
|---|---|---|
| Static key in `X-API-Key` | **Chosen** | Supported natively by the platform's header secrets; the secret holds the bare key |
| Static token in `Authorization: Bearer` | Close second | Same strength, more standard header. But the platform needs the secret's value to include the `Bearer ` prefix (`Bearer [[X]]` is sent literally), which is an easy misconfiguration. The usual advantage, that `Authorization` is redacted by default, is moot: the platform never logs secrets and the service logs only fingerprints |
| Key in the query string | Rejected | Leaks into access logs, analytics and error reports |
| HTTP Basic | Rejected | Same strength as a static token, with clumsier semantics |
| OAuth 2.0 client credentials | Rejected | No native support; it would need an issuer plus a token-fetching Automation and refresh-on-401 logic in the conversation. Short-lived tokens are not worth that machinery for public catalogue data |
| Self-signed JWT | Rejected | The platform would still store one static token, so expiry only forces manual rotation |
| HMAC request signing, mTLS | Rejected | The platform cannot sign requests or present client certificates |
| IP allowlist | Not now | The platform does not document stable outbound IPs. Could be added later as an extra layer, not as a replacement |

### Decision

- A static API key in `X-API-Key`, over HTTPS only.
- The service accepts a set of keys, with one key per consumer and environment: `platform-test` and `platform-prod` (the Test and Production values of the `CATALOG_API_KEY` workspace secret), plus `local-dev`.
- A per-key rate limit with `429 rate_limited`.

### Consequences

- Rotation without downtime: add the new key, update the secret, remove the old key (see *Key rotation* above). This works because the service accepts more than one key, not because of the header choice.
- Separate Test and Production keys mean a key leaked from test conversations can be revoked without touching production.
- Keys never expire. Rotation is a procedure that has to be followed, not something enforced.
- Moving to Bearer later is a small change: a different header in the auth dependency, and a secret value with the `Bearer ` prefix.

**Revisit if**: the service gains write operations or per-customer data, a second external consumer appears, or the platform adds native OAuth 2.0 credentials.
